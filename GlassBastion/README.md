# GlassBastion — predictable credential encryption in JumpServer (CWE-338 / CWE-330)

*Wildcard finding. Easy-to-exploit low-entropy crypto in a very high-value target: a
leading open-source **Privileged Access Management / bastion host**.*

| Field | Value |
| --- | --- |
| Target | **JumpServer** (`jumpserver/jumpserver`) — open-source PAM/bastion, ~25k★, enterprise-deployed |
| Component | `apps/static/js/session-encrypt.js` — client-side credential encryption |
| Type | **CWE-338** Use of Cryptographically Weak PRNG (+ **CWE-330** insufficient entropy, **CWE-327** ECB) |
| Impact | Predictable AES/SM4 key protecting login & **privileged asset** passwords → credential recovery |

## The bug

JumpServer encrypts passwords in the browser before sending them to the backend.
The symmetric key that protects the password is generated with **`Math.random()`**:

```js
// apps/static/js/session-encrypt.js  (RSA path)
function rsaEncryptPassword(password, rsaPublicKey) {
    const aesKey = (Math.random() + 1).toString(36).substring(2);   // <-- CWE-338
    const keyCipher = rsaEncrypt(aesKey, rsaPublicKey);
    const passwordCipher = aesEncrypt(password, aesKey);
    return `${keyCipher}::encrypted::${passwordCipher}`;
}
function aesEncrypt(text, originKey) {
    const key = CryptoJS.enc.Utf8.parse(fillKey(originKey));
    return CryptoJS.AES.encrypt(text, key, {
        mode: CryptoJS.mode.ECB,            // <-- CWE-327 (ECB)
        padding: CryptoJS.pad.ZeroPadding
    }).toString();
}
// The GM (SM2/SM4) path has the same flaw: the SM4 key is randomString(16),
// where each char is "…".charAt(Math.floor(Math.random() * 62))  // also Math.random
```

Source: `https://github.com/jumpserver/jumpserver/blob/dev/apps/static/js/session-encrypt.js`
(L68 `aesKey`, L14–20 `aesEncrypt`/ECB, L151–160 `randomString`; present on `master`, `dev`, `v4`).

Two independent problems, both fatal for a key:

1. **Non-cryptographic PRNG.** `Math.random()` is V8's `xorshift128+`, *not* a CSPRNG.
   Its internal state is fully recoverable from a handful of outputs, after which
   every past/future output — including the one used to build this key — is
   **predictable**. A credential key must come from `crypto.getRandomValues()`.
2. **≤52 bits of entropy.** The whole key derives from a single `Math.random()`
   double (52-bit mantissa), rendered as ~10 base-36 chars and zero-padded to 16
   bytes. So an "AES-128" key carries at most 52 bits — and in practice is
   predictable (point 1), not merely short. ECB mode adds a deterministic-block leak.

## Why it matters

JumpServer is a **bastion / PAM** — its entire job is to broker and protect
privileged credentials (SSH/RDP/database/asset passwords). This routine encrypts
exactly those secrets. The ciphertexts travel in requests and routinely land in
places an attacker can read (reverse-proxy/WAF logs, browser history, SIEM, audit
trails, or a co-resident/same-origin script). Protecting the crown-jewel
credentials with a *predictable* key defeats the control.

## Proof of concept

`predict.py` is a working **V8 `Math.random()` predictor** (recovers `xorshift128+`
state with z3 and inverts V8's 64-value cache ordering). `victim.js` reproduces
JumpServer's `rsaEncryptPassword` exactly (incl. AES-ECB/ZeroPadding and a real RSA
keypair for the server). `attacker.py` uses **only** a few leaked `Math.random()`
samples and the captured `passwordCipher` — never the RSA private key — to predict
the key and decrypt the credential.

```
./run.sh
```

## Exploitability / threat model (honest)

- **Unconditional weakness:** the credential-wrapping key is generated by a
  non-cryptographic, predictable PRNG with ≤52-bit entropy, under ECB. This is a
  real cryptographic defect regardless of deployment.
- **Full plaintext recovery** additionally needs (a) the credential ciphertext
  (captured from logs/history/proxy or a co-resident script) and (b) a few
  `Math.random()` outputs from the victim's V8 realm to seed the predictor
  (same-origin XSS, a malicious browser extension, a shared/3rd-party script, or any
  app value derived from `Math.random()` that reaches the attacker). Both are
  realistic for a web-facing admin console.
- The PoC demonstrates the hardest part — recovering the key purely from
  `Math.random()` predictability — and the complete credential decryption.

## Remediation

- Generate key material with **`crypto.getRandomValues()`** (Web Crypto), never
  `Math.random()`.
- Use an **AEAD** (AES-GCM) with a random nonce instead of AES-ECB.
- Prefer delegating transport confidentiality to TLS and hashing/secret-storage to
  the server; if client-side wrapping is kept, wrap a CSPRNG key directly under the
  server public key (RSA-OAEP) with no `Math.random()` anywhere in the path.
